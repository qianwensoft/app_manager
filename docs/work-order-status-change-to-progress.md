# 工单状态变更说明自动记录到进展

## 功能概述

工单状态变更（标记解决、关闭工单、重新打开）时填写的说明会自动记录到工单进展中，方便查看处理历史。

## 更新内容

### 1. 重新打开工单支持填写说明

**之前**: 重新打开工单时无法填写说明，只有关闭和解决时可以填写。

**现在**: 重新打开工单时也会弹出输入框，允许填写重新打开的原因。

### 2. 状态变更说明自动记录到进展

**之前**: 状态变更的说明只记录在时间线（activity）中，需要切换到时间线标签页查看。

**现在**: 如果填写了说明，会自动创建一条工单进展记录，格式为：
```
[状态变更：已解决] 测试通过，问题已修复
[状态变更：已关闭] 用户确认问题解决
[状态变更：重新打开] 问题复现，需要进一步排查
```

## 实现细节

### 后端实现

**文件**: `server/api/work_order.go`

**关键代码**:
```go
// applyWorkOrderStatus 共用：内部接口与开放 API 第三方调用都走它。
func applyWorkOrderStatus(c *gin.Context, wo *models.WorkOrder, status, comment string, actorUserID uint, actor string) {
	// ... 状态更新逻辑 ...
	
	// 如果状态变更有说明，自动创建工单进展
	if strings.TrimSpace(comment) != "" {
		statusLabel := workOrderStatusLabel(status)
		progressContent := fmt.Sprintf("[状态变更：%s] %s", statusLabel, strings.TrimSpace(comment))
		progress := models.WorkOrderProgress{
			WorkOrderID: wo.ID,
			Content:     progressContent,
			CreatedBy:   actorUserID,
			CreatorName: actor,
		}
		database.DB.Create(&progress)
	}
	
	// ... 事件推送逻辑 ...
}
```

**工作流程**:
1. 检查 comment 是否非空
2. 获取状态的中文标签（已解决/已关闭/重新打开）
3. 格式化进展内容：`[状态变更：{状态}] {说明}`
4. 创建工单进展记录
5. 记录操作人和时间

## 使用场景

### 场景 1: 标记解决并记录原因

1. 技术人员完成问题处理
2. 点击"标记解决"按钮
3. 在弹出框输入："更换了损坏的电源模块，设备恢复正常"
4. 确认后：
   - 工单状态变为"已解决"
   - 时间线记录状态变更
   - 进展中新增一条：`[状态变更：已解决] 更换了损坏的电源模块，设备恢复正常`

### 场景 2: 关闭工单并记录确认信息

1. 用户确认问题解决
2. 点击"关闭工单"按钮
3. 在弹出框输入："用户现场验收通过"
4. 确认后：
   - 工单状态变为"已关闭"
   - 时间线记录关闭操作
   - 进展中新增一条：`[状态变更：已关闭] 用户现场验收通过`

### 场景 3: 重新打开工单并说明原因

1. 发现问题复现
2. 点击"重新打开"按钮
3. 在弹出框输入："问题在高温环境下仍会出现，需要进一步排查"
4. 确认后：
   - 工单状态变为"重新打开"
   - 时间线记录重新打开操作
   - 进展中新增一条：`[状态变更：重新打开] 问题在高温环境下仍会出现，需要进一步排查`

### 场景 4: 快速状态变更（不填说明）

1. 点击状态变更按钮
2. 弹出框留空或直接点击取消
3. 工单状态更新，但不创建进展记录（只记录到时间线）

## 优势对比

### 之前的流程

```
技术人员：标记解决 → 填写说明 → 确认
系统：更新状态 + 时间线记录说明
查看者：需要切换到时间线标签页才能看到说明
```

### 现在的流程

```
技术人员：标记解决 → 填写说明 → 确认
系统：更新状态 + 时间线记录 + 进展记录
查看者：在进展列表直接看到状态变更说明，无需切换标签页
```

## 状态标签映射

后端使用 `workOrderStatusLabel` 函数将状态码转换为中文标签：

| 状态码 | 中文标签 |
|--------|---------|
| `resolved` | 已解决 |
| `closed` | 已关闭 |
| `reopened` | 重新打开 |
| `in_progress` | 进行中 |
| `open` | 待处理 |

✅ **完全向后兼容**

- 已有的时间线记录不受影响
- 不填写说明时行为与之前一致（不创建进展）
- 进展记录格式清晰，带有 `[状态变更：xxx]` 前缀，易于区分

## 注意事项

1. **说明可选**: 用户可以选择不填写说明，这种情况下不会创建进展记录
2. **格式统一**: 进展内容以 `[状态变更：{状态}]` 开头，便于识别和过滤
3. **操作人记录**: 进展记录会保存操作人信息（CreatedBy 和 CreatorName）
4. **时间戳**: 自动记录创建时间，与状态变更时间一致
5. **实时刷新**: 前端状态变更后会自动刷新进展列表，无需手动刷新
